# UniGuard：UniVPN 隧道守护程序

## 目标

无人值守环境下，**始终监控隧道，断了就尽一切办法连回来**。不依赖原客户端的人工操作。

## 形态

| 组成 | 位置 | 权限 | 作用 |
|---|---|---|---|
| 菜单栏守护 App | `~/Applications/UniGuard.app` | 用户 | 探测状态、分级恢复、记录状态 |
| 用户 LaunchAgent | `~/Library/LaunchAgents/work.zhaolei.uniguard.plist` | 用户 | 登录自启，进程被杀了自动重启 |
| root 路由修复器 | `/usr/local/libexec/uniguard-routefix.sh` + `/Library/LaunchDaemons/work.zhaolei.uniguard.routefix.plist` | root | 开机自启，清理残留路由（无需密码） |

## 任务栏图标（常驻）

图标 + 文字，一眼可见：

| 图标 | 文字 | 含义 |
|---|---|---|
| 实心锁盾 | 在线 2h13m | 隧道正常，显示已连时长 |
| 半盾 | 重连中 | 引擎在但隧道没起来 |
| 斜线盾 | 引擎停 | 引擎进程不存在 |
| 感叹盾 | 残留路由 | 有指向已消失 utun 的路由 |
| 铃铛 | 弹窗阻塞 | 客户端弹了「返回码超时」之类 |
| 三角警告 | 隧道异常 | 接口在但网关不可达 |

点开菜单可看：状态、隧道名与 VIP、引擎/网关通断、已连时长、重连与断开次数、上次动作、**最近 12 次状态变化**。

## 故障判定与处置矩阵

| 探测到的故障 | 判据 | 处置顺序 |
|---|---|---|
| 引擎未运行 | `pgrep -x UniVPNCS` 为空 | 启动客户端 → 等自动登录 → 不行再点「连接」 |
| 连接未成功 | 引擎在、无 VIP、无弹窗 | 点「连接」→ 指数退避（15s→240s）→ **连续 3 次失败且距上次重启 >90s → 杀进程重建会话** |
| 返回码超时（弹窗） | 读客户端窗口文字含「超时」/「重新启动客户端」 | 点「确定」关弹窗 → 重启客户端换新会话 → 25s 冷却 |
| 残留路由 | `netstat` 里路由指向不存在的 utun | 写触发文件 → root 修复器立即 `route delete` → 20s 冷却 |
| 隧道不通 | 有 VIP 但 `nc -z 网关 1024` 失败 | 观察 → 距上次重启 >120s 则重建隧道 |
| 系统唤醒 | `NSWorkspace.didWake` | 立即探测，不等周期 |

### 恢复阶梯（由轻到重，逐级升级）

| 级别 | 动作 | 触发条件 |
|---|---|---|
| 一级 | 点「连接」 | 引擎在、无隧道 |
| 二级 | 只退出 GUI 再重开（引擎随之退出） | 连续 3 次点连接无效 |
| **三级·终极兜底** | **完全退出 UniVPN（含 `UniVPNCS` 引擎与 `UniVPNPromoteService`）→ 等进程彻底消失 → 清残留路由 → 重新启动 → 自动登录** | 连续 6 次失败、或二级重启两次仍无效、或隧道假连（有 VIP 但网关不通） |

三级兜底的每一步都带等待与校验：优雅 `quit` → 强杀 → 轮询确认三个进程全部消失（最多 7 秒）→ 触发 root 修复器清路由 → 等 3 秒 → 启动 → 等 8 秒自动登录 → 再补点一次连接。

也可以外部强制触发，便于脚本或远程运维：
```sh
touch /tmp/uniguard.fullrestart.trigger     # 下一个周期内执行终极兜底
```

菜单里也有「彻底重启客户端」（快捷键 ⇧⌘R）可直接手动试。

其余保护：任何时刻连续失败过密会走退避，最大 240s；`killall` 只杀客户端（引擎随 GUI 退出），不需要 root。

- 路由修复日志：`/var/log/uniguard-routefix.log`

## 实测

1. **拉起验证**：VPN 全断（引擎/utun 均无）时启动守护，自动拉起客户端并连上，VIP `172.16.21.54`。
2. **回归验证**：`killall -9 UniVPN` 后隧道全灭，守护于下一个周期（日志 `09:42:24 动作：启动客户端`）自动恢复，隧道重建为 `172.16.21.98`，全程无人干预。
3. **路由修复器**：以 root 常驻，`job state = running`，`last exit code = never exited`。
4. **终极兜底验证**：外部触发 `fullrestart`，日志完整记录「完全退出并重启 → 启动客户端 → 点击结果 nowin（客户端已自动登录）」，隧道重建为 `172.16.21.76`。

## 已知限制

- 首次需在「系统设置 → 隐私与安全性 → 自动化」放行 UniGuard 控制 System Events，否则点不动按钮（届时图标显示弹窗阻塞，日志写空结果）。
- 「返回码超时」若来自网关侧限流/账号被踢，重启会话可能仍失败；此时守护会持续退避重试并记录，不会放弃。
- 状态计数按本次进程运行期统计，重启守护会归零（历史仍留在日志里）。

## 多配置档：重连回断线前那一档

客户端自己记「上次连接的档」，但它可能与你断线时用的不是同一档。UniGuard 不依赖它：

1. **记录**：每次探测到正常，从客户端窗口 `VPN名称：` 右侧读出档名，记为「断线前档位」
2. **写回**：需要重启客户端前，把 `~/.UniVPN/sysconfig.ini` 的 `ClientLastAccessSession` 写成该档（UTF-8，值形如 `xxx.ini`）
3. **启动**：再启动客户端，它按写回的档自动登录
4. **锁定（可选）**：菜单「目标配置档」可手动指定一档；默认「跟随断线前档位」

实测：把 `ClientLastAccessSession` 故意改成另一档后触发彻底重启，日志出现
`配置档：写回 xxx.ini`，最终连回原档，VIP 正常。

注意：客户端配置档列表是 Qt 自绘，AX 读不到行文本，点行不可靠，所以采用"写配置"而非"点列表"。

## 残留路由清理：按档位定向 + 绑进失败阶梯（v1.2）

### 为什么必须做
客户端连上时会执行 `route add -host <网关> <隧道内地址>`；异常退出后 utun 被销毁，这条主机路由却留在表里。此后所有发往网关的 SYN 都被它带进黑洞 —— 现象就是"点连接没反应 / 返回码超时 / 重启多少次都连不上"，而手工 `sudo route delete <网关>` 立刻恢复。

### 触发时机（不是旁路轮询，是失败阶梯的一部分）
| 时机 | 动作 | 等待 |
|---|---|---|
| 二级重启（重启 GUI） | `killall -9 UniVPN` 之后、启动客户端之前 | 最多 8s |
| 三级兜底（完全退出重启） | 第 ④ 步，退出/killall 全部进程之后 | 最多 10s |
| 拨号连续失败 ≥2 次（`dialTimeout`） | 立刻请求一次，90s 内不重复 | 最多 8s |
| 掉线刚被检测到（`ok -> 异常`） | 预清一次，60s 内不重复 | 最多 4s |

等待方式是**轮询路由表直到真的干净**，而不是写完触发文件就继续启动。

### 定向
触发文件 `/tmp/uniguard.routefix.trigger` 的内容是**当前配置档的网关 IP**；root 修复器读它并优先清理该网关，再清其它已知网关，不误伤另一档的路由。

### 两种残留形态（都要认）
1. `125.71.210.99 → utun7 UGHS`，而 utun7 已不存在；
2. `125.71.210.99 → 172.16.99.2 UGHS en0`，接口看着正常，但下一跳落在隧道地址池、且该地址不被任何存活 utun 拥有。

**关键坑**：`route -n get <网关>` 会被内核自动生成的 `/32` 克隆路由（`→ 物理网关 UGCS en0`）掩盖，读到的是"正常"结果，因此**必须直接扫 `netstat -rn -f inet` 表**判断。

### 实测
- 造坏路由：`ifconfig utun99 create` + 赋 `172.16.99.1/172.16.99.2` + `route add -host <网关> 172.16.99.2` + `ifconfig utun99 destroy`
- root 侧日志：`删除网关坏路由 125.71.210.99（下一跳 172.16.99.2 属于隧道池且已不存在）`
- 守护侧日志：`请求清理残留路由（目标网关 125.71.210.99）：兜底重启前清理` → `残留路由已清空` → 写回档位 → 启动客户端 → 隧道恢复


## DNS 守护：清掉客户端硬塞的 DNS（v1.6）

### 现象
UniVPN 每次连上，会把 `61.139.2.69` 加到当前网络服务（如 Wi-Fi）的 DNS 列表**第一位**。
系统优先用它解析，该服务器在隧道外的网络里经常不响应，于是表现为：
隧道、网关都通，但浏览器/终端域名全部超时 —— 「VPN 连上了反而上不了网」。

`networksetup -getdnsservers "Wi-Fi"` 可以看到它在最前面：
```
61.139.2.69
8.8.8.8
223.5.5.5
114.114.114.114
```

### 为什么放在 root 修复器里
`networksetup -setdnsservers` 明确要求管理员权限（非 root 直接 `Error: Command requires admin privileges`，返回码 14）。
UniGuard 已有 root 常驻的 `com.uniguard.routefix`，把 DNS 巡检挂进去即可，**不用再要一次密码、也不用额外常驻进程**。

### 规则
| 项 | 值 |
|---|---|
| 巡检周期 | 每 2 轮（约 8 秒），另加启动时、收到触发文件时立即执行 |
| 黑名单 | 默认 `61.139.2.69`；可在 `/usr/local/etc/uniguard/bad-dns.txt` 每行一个追加 |
| 处理方式 | 从该服务的 DNS 列表里**只删黑名单条目**，顺序与其余条目保持不变；删空则 `-setdnsservers <服务> Empty`（走 DHCP） |
| 暂停 | 菜单「暂停 DNS 守护」或 `touch ~/.uniguard/dns-guard.off` |
| 手动触发 | 菜单「立即清理 VPN DNS」（⌘D）→ 写 `/tmp/uniguard.dnsfix.trigger` |

### 两侧日志
root（`/var/log/uniguard-routefix.log`）：
```
[2026-11-18 12:05:33] routefix 启动（DNS 黑名单：61.139.2.69 ）
[2026-11-18 12:05:33] DNS：Wi-Fi 删除 61.139.2.69，保留 8.8.8.8 223.5.5.5 114.114.114.114
```
用户级（`~/Library/Logs/UniGuard.log`）：
```
[12:05:26] DNS：请求清理（Wi-Fi:61.139.2.69）
[12:05:41] DNS：已清理，DNS 恢复正常
```
菜单同时显示 `DNS 守护：正常 / 待清理 Wi-Fi:61.139.2.69 / 已暂停`。

### 实测
1. 手工把 `61.139.2.69` 设回 Wi-Fi DNS 首位；
2. 8 秒内 root 日志出现「DNS：Wi-Fi 删除 61.139.2.69，保留 …」；
3. `networksetup -getdnsservers "Wi-Fi"` 不再含该地址，`nslookup www.baidu.com` 正常返回。

### 注意
如果某个内网域名**只**能由该 DNS 解析，删掉后会解析失败。此时把该地址从黑名单里去掉（或暂停 DNS 守护），
改为在「系统设置 → 网络 → 高级 → DNS」里把它排到最后一位即可。

## 退出与启动联动（v1.7 / v1.8）

### 退出（菜单「退出守护」，或 `touch /tmp/uniguard.quit.trigger`）
1. 退出 UniVPN：先 AppleScript `quit`，2 秒后 `killall -9 UniVPN UniVPNCS UniVPNPromoteService`，再确认进程消失；
2. 让 root 端立即清一次 DNS 并等到真的干净（客户端退出后常把 `61.139.2.69` 留在列表里）；
3. 写 `~/.uniguard/quit.flag`，以退出码 0 结束。

LaunchAgent 用 `KeepAlive.SuccessfulExit=false`：**正常退出不重启，崩溃/被强杀仍由 launchd 拉起**。

### 再启动：反向守护 com.uniguard.watch
`~/Library/LaunchAgents/com.uniguard.watch.plist` 每 5 秒跑一次 `uniguard-watch.sh`：

```
读 ~/.uniguard/vpn.state（上一轮的 0/1）→ 与当前 pgrep -x UniVPN 对比
  0 → 1（VPN 刚启动）：删掉 quit.flag
  VPN 在跑 + 有 quit.flag      → 什么都不做（尊重用户退出）
  VPN 在跑 + 无 quit.flag + 守护没在跑 → launchctl kickstart com.uniguard.agent
```

因此：
| 操作 | 结果 |
|---|---|
| 点「退出守护」 | 守护和 VPN 一起退出，保持退出（不会被自己拉回来） |
| 之后手动启动 UniVPN | 5 秒内守护自动起来 |
| 守护崩溃 / `kill -9` | launchd 立即重启 |
| 手动打开 UniGuard.app | 启动并清除 `quit.flag` |

### 启动观察期（v1.8.1）
守护刚启动的 30 秒内不点「连接」、不重启客户端（`启动观察期，等客户端自己登录`）；
「隧道起来了但不通」也不再立刻兜底，而是**持续 60 秒**不通才重建。避免守护刚被拉起就和客户端自己的自动登录抢操作。

### 实测
```
[12:52:30] 退出守护（外部触发） → 动作：退出客户端（随守护一起退出）
[12:52:33] 客户端已全部退出
[12:52:34] DNS：当前干净（退出客户端后）
（20 秒后守护仍为 -，未被拉起）
[12:54:34] watch：检测到 UniVPN 启动，已拉起守护
[12:54:35] 守护启动 interval=15s gateway=125.71.210.99
```
